# ADR 0023: Relay forwarding uses an explicit allowlist

**Status:** Accepted

## Context

A relay accepts a CONNECT request and can reach destinations that the client cannot reach directly. An implicit or broadly permissive forwarding rule would make the relay an uncontrolled proxy. Multi-hop routes also need to keep relay addresses, destination resolution, and credentials outside domain objects.

## Decision

`relay-adapter` defines `RelayForwardingPolicy`. Each `RelayServer` receives one policy that contains an explicit set of `RelayTarget` values. The server accepts a CONNECT request only when its target is in that set. It returns a generic HTTP 403 response for a denied target and does not expose the target through domain events.

`RelayClient` implements `TunnelTransport` for TCP only. It supports `Relay`, `RelayThenSocks5`, and `TwoRelaysThenSocks5` plans. Each relay hop uses CONNECT. The final SOCKS5 handshake runs inside the established relay tunnel. UDP route planning rejects every relay topology before establishment.

Address and credential resolvers run at the adapter boundary. They map opaque endpoint, destination, and credential references to network addresses and secrets. The domain model never contains those values.

## Consequences

Relay operators must configure every forwarding target before accepting traffic. The local contract tests run a one-relay and a two-relay route through a SOCKS5 fixture and an echo endpoint. Planner tests prove that relay routes reject UDP and same-operator hops when the policy requires operator separation.

## Alternatives

A callback authorization rule was rejected because its behavior would not be inspectable as data. A denylist was rejected because new targets would be allowed by default. Direct UDP support was deferred until an adapter advertises and implements it.

## Testing

Run `cargo test -p relay-adapter --test contract` for relay forwarding and multi-hop behavior. Run `cargo test -p route-core --test topologies` for route capability and operator checks.
